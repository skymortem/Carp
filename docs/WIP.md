## Почему моточасы были прочерком

Проверено на живом устройстве (S96v2, CAN 4852) через `/starline/api-raw`:

```
data.state.motohrs  = null     ← всегда, счётчик наработки не заполняется
data.common.motohours_reset_ts = 1791429513   (08.10.2026 — сброс счётчика)
```

`parse_snapshot` честно превращал `null` в `None`, а дашборд показывал «—».
События StarLine при этом отдают пары с точностью до секунды:

| код | смысл | код | смысл |
|-----|-------|-----|-------|
| 1037 | Двигатель запущен | 1042 | Двигатель остановлен |
| 1065 | Зажигание включено | 1064 | Зажигание отключено |
| 601/605/613–620 | пуски по способу | 602/606/621–628 | остановки по способу |

Реальный журнал за 30 дней: **244 сессии, 43 ч 58 мин** (за неделю ~9 ч 51 мин) —
числа правдоподобные, поэтому наработку считаем сами.

## Что сделано в этой ветке

- **`services/enginetime.py`** — пары «запуск/остановка» → таблица `engine_sessions`
  (`car_id`, `started_at` уникальны, повторный разбор окна не плодит дубли).
  Накопительные моточасы = сумма интервалов до момента снимка; незакрытая сессия
  считается «по сейчас». Если устройство всё-таки отдаёт `state.motohrs`, его
  значение главнее.
- **`StarLineClient.get_events()`** — `POST /json/v2/device/{id}/events` окнами по
  суткам (`period_start`/`period_end`), журнал хранится 30 дней.
- **`collection.collect_and_store`** — после сохранения снимка пишет ему моточасы и
  один раз заполняет пустые исторические снимки (`backfill_snapshots`).
- **Заправки** — `services/fuel.py`: прирост `obd.fuel_litres` ≥ `FUEL_FILL_MIN_LITRES`
  (5 л) между соседними снимками → строка в `fuel_fills` (объём = разница уровней).
  Рост двумя шагами в течение 3 ч склеивается в одну заправку.
- **Telegram-бот** — `services/telegram.py`, свой long polling на httpx (без
  библиотек), стартует в `lifespan` рядом с планировщиком. Спрашивает цену литра,
  принимает `59.9`, `59,90 ₽`, `/skip`; сохраняет цену и стоимость = цена × объём.
  Offset апдейтов переживает перезапуск (`app_state.telegram_offset`).
- **UI** — карточка «Заправки» на дашборде (последние 5 + итоги), блок «Telegram-бот»
  на `/setup` (токен, chat_id, проверка связи), `GET/POST /settings/telegram`.
- **Миграция `0004_engine_fuel`** — `engine_sessions`, `fuel_fills`, `app_state`,
  идемпотентная как предыдущие.

## Команды

```bash
# локальный запуск (из backend, один worker)
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
PYTHONPATH="" uvicorn app.main:app --host 0.0.0.0 --port 8000

# тесты
python -m pytest tests -q          # 89 passed, отдельная временная SQLite, StarLine замокан

# миграции
alembic revision --autogenerate -m "..."   # из backend
alembic upgrade head                       # или просто перезапустить сервис
alembic check                              # должно быть "No new upgrade operations detected"

# деплой на сервер (carp-app.ru, 77.232.143.108, systemd + nginx)
sudo /opt/carp/deploy/backup.sh
cd /opt/carp && sudo -u carp git pull && sudo systemctl restart carp
journalctl -u carp -n 30 --no-pager | grep -iE "миграц|моточас|Telegram"
```

`.env` на сервере после деплоя должен получить `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID` — их пишет `/setup` (файл должен быть записываемым для `carp`).

## Грабли, на которые уже наступали

- **Один процесс Uvicorn.** Планировщик, кеш StarLine и **long polling Telegram**
  живут в процессе: с `--workers 2` будет двойной сбор и двойные ответы бота.
- **`WorkingDirectory` = `backend`.** `DATABASE_URL` и `.env` — относительные пути;
  `/setup` пишет в `.env`, каталог должен быть записываемым.
- **`STARLINE_*` и `TELEGRAM_*` не задавать в systemd** — переменные окружения
  приоритетнее `.env`, и `/setup` перестанет на них влиять.
- **`create_all()` и миграции расходятся.** Тесты строят схему через `create_all`,
  поэтому новые миграции обязаны проверять существование колонок/таблиц.
  Сверка: `alembic check`.
- **SQLite хранит `ts` без таймзоны.** Сравнения — наивный UTC; наружу отдаём ISO
  с `+00:00`, иначе браузер посчитает возраст со сдвигом. `engine_sessions` и
  `fuel_fills` — тоже наивный UTC.
- **Журнал событий StarLine — 30 дней.** Если сервис лежал дольше, раннюю наработку
  не восстановить: счётчик начнётся с первого доступного пуска.
- **Объём заправки приблизительный.** Уровень топлива снимается раз в час: если
  между снимками успели проехать, часть топлива уже сгорела. Порог 5 л отсекает
  шум датчика, но не компенсирует пробег.
- **Погода — внешняя зависимость.** `services/weather.py` ходит в Open-Meteo с
  таймаутом 4 с; ошибка → `outside_temp = null`, сбор не падает.
- **Консоль — только чтение.** Команды StarLine (`set_param`, `async`, `controls`)
  не проходят и до API не доходят; это проверено тестом.
